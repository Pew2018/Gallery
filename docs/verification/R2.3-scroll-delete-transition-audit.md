### 观察到的事实

- 所附 MP4 为 576×1280、30 FPS、28.8667 秒。约 14.75 秒的抽帧可见网格上半区成片空白，随后缩略图恢复；该帧本身不能表明 ViewHolder 是否曾显示同一媒体、是否被重新绑定或 Glide 是否取消请求。
- 没有随录屏提供的 Gallery 诊断导出、Perfetto/FrameMetrics 或设备 logcat。录屏能证明空白现象，不能证明图片加载根因。
- `MediaAdapter.setupThumbnail()` 仅当 request key 改变时取消旧 Glide/Picasso 请求、清空 drawable 并加载。key 含规范化加载路径、`Medium.getKey()`（路径/修改时间/大小和内容失效版本）、媒体类型、裁切、圆角、GIF 动画、滚动方向、旋转标记。`onViewRecycled()` 正常取消离屏请求并清 Drawable。
- 列表层已具备同内容提交跳过、缓存预览 append 快速提交、纯媒体重排路径、后台 Diff 单飞、滚动及 Viewer return 时延后发布、generation 丢弃旧 Diff、稳定路径 identity 和时长 payload。Diff 内容策略不比较 Room ID、MediaStore ID 和 grid position。
- Adapter 创建路径由 `MediaActivity.setupAdapter()` 在 adapter 缺失时执行。此分支的 layout animation 只用于列表样式首次设置；没有看到普通扫描通过重建 Adapter 清空网格。Adapter 配置禁用 `itemAnimator`，因此不是当前白屏证据的直接解释。
- Viewer 的返回结果此前只传 `EXTRA_RETURN_PATH`（离开 Viewer 时的当前媒体）。普通成功删除由 `hideDeletedMedium()` 更新 Viewer catalog，但没有把删除路径送到来源 Activity。网格只有旧列表与返回目标 path；异步恢复扫描才会最终移除删除项。此链路可直接解释“Viewer 已显示下一张，来源网格仍含旧项目”的竞态。
- Viewer 只有在底层 `tryDeleteFileDirItem`/回收站搬移回调报告成功后才调用 `hideDeletedMedium()`；失败走 refresh/toast，不会进入成功隐藏路径。文件删除回调还核实源路径不存在以及回收站副本条件。
- 共享元素进入/退出都使用 `PhotoViewerTransition.DURATION_MS`（当前 120ms）与同一个 Oxygen easing，遮罩 fade 同为 120ms。全屏控件 chrome 采用 225ms enter / 195ms exit。没有依据将时长机械改长：当前仍需设备帧时间验证。

## R2.3 代码修改

- Viewer 累积当前 Viewer 会话内**确认成功**的删除路径，在 `RESULT_OK` 中通过 `EXTRA_DELETED_PATHS` 返回。
- Activity reenter 读到路径后，先记录 Activity 生命周期内的确认删除 tombstone、过滤 `mMedia`，并经 MediaAdapter 正常 path Diff 移除。Viewer return 目标查找等删除提交完成后才继续，仍然按稳定 path 获取目标和保持滚动位置。
- 后续缓存预览和扫描发布继续过滤这些成功删除路径，避免先前缓存或过期快照让项目复活；Viewer 没有成功删除时不会发出路径。
- 删除过滤同时移除没有剩余媒体的分组标题。Adapter 保持原单飞 Diff 与可见锚点恢复路径。
- 删除 Viewer 中最后一项、返回结果没有媒体 path 时，也独立应用成功删除集合；回归测试覆盖空结果和来源列表清空。
- 新增回归覆盖 Activity reenter 先删除来源网格再映射邻项、以及分组标题清理。
