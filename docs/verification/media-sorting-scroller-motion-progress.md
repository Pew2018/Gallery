## Stage reports

### Stage 1 investigation notes

- Confirmed `MediaPagePreview` merges candidates by path and sorts cumulative snapshots before publication. Scan updates are guarded by the active load request, terminal state, and current access checks. Ordinary physical scans retain metadata needed for sort changes; photo-profile loading sorts cache, indexed, cumulative filesystem, and final snapshots.
- Confirmed one reproducible ordering defect in the cache source: `MediumDao.getPreviewMedia()` always applied `last_modified` ordering and a `target * 4` SQL limit. A later in-memory sort could not recover the configured prefix from candidates omitted by that query. This affected normal folders and root cache previews across sort modes.
- Changed the DAO to return all cached rows matching folder/type, then added `CachedMediaPreviewOrder` to normalize date-taken fallback, sort by the configured comparator, and deterministically choose random cache candidates independent of Room row order. Cache access checks still stop after the requested number of valid preview items.
- Added a synthetic 5,000-row regression comparing the cached prefix to the actual app comparator for ascending/descending date taken, modified time, name, numeric name, path, numeric path, size, and deterministic random selection. Focused `MediaPagePreviewTest`: 8 tests passed after fixing duplicate paths in the test fixture.
- Added a real-file device integration using 1,000 tiny MediaStore images with reverse-ordered padded names. It changes the album's selected sort to ascending name, waits for `displayedMediaIsFinal` and 1,000 adapter items, and confirms the entire final grid matches the expected order. Pixel_4/API 29 passed; settings and fixture rows are restored/removed after the test.
- Expanded the file-backed device integration to unpadded numeric names and 11 configured modes: ascending/descending lexical name, numeric name, date taken, modified time, path, and size. Each mode starts a new refresh, waits for the matching request generation to commit a complete 1,000-item adapter, rejects missing/duplicate paths, and compares the displayed order to the selected comparator. Pixel_4/API 29 passed.
- Extended the 41-file custom photo profile UI case to store reversed numeric filenames, select configured ascending name order, and assert the complete profile grid is actually ordered before entering and returning from Viewer. Pixel_4/API 29 passed.
- The Activity regression `progressivePageRegroupsCorrectedRowsAndRejectsOldSortingAfterCompletion` exercises a 11,023-row progressive snapshot, changes sorting while scanning, verifies the immediate grouped order, commits the final scan, and rejects stale partial rows. The complete JVM suite passed under Java 21.
- Performance risk to measure: complete Room candidate retrieval and in-memory sort now occur for the cache preview, though disk access validation remains bounded to candidates until the preview fills. No measured user-device timing yet.

### Stage 2 investigation notes

- The previous policy tied availability to a complete scan or an exact index/display count. That hid a valid thumb while the currently published rows already occupied a scrollable range.
- Visibility now waits for the grid's next pre-draw and compares the active orientation's computed range and extent. A generation token prevents stale pre-draw callbacks from exposing the thumb after a later empty-state update.
- Focused `MediaFastScrollerPolicyTest` passes. `:app:assembleFossDebug` succeeds; the updated APK installs and launches on the API 29 Pixel_4 AVD. The emulator contains the 1,000-image `SortRegression` folder. An accessibility dump confirms a scrollable grid; a screenshot shows the grid after loading, but the current emulator session did not capture a deliberately partial scan or prove range synchronization while rows are being added. Stage remains IN_PROGRESS.

### Stage 3 investigation notes

- The exact bundled fast-scroller AAR was inspected. Its thumb touch callback mixed `MotionEvent.rawX/rawY` with `track.getLocationInWindow()`, and its idle animation scaled the handle to zero. A device regression initially observed a 1,021 px list offset reset to 0 during a thumb drag.
- Media and folder grids now use screen-space track geometry and RecyclerView pixel scroll range/extent to map each drag event; the existing 28 dp touch target remains, and the handle stays at unit scale while the gallery is active. MainActivity and MediaActivity both install the gallery touch path; MediaActivity still reports engaged/released state to protect scroll restoration while dragging.
- The drag test first exposed its own bad starting anchor (the activity restored near the end of the list); after forcing a known top position, the real 60-image grid passed a middle → bottom → top → repeated bottom sequence on Pixel_4/API 29, with every assertion reading the RecyclerView's actual pixel offset. `FolderPickerPolishTest.galleryDragMapsTheVisibleTrackToTheRealPixelScrollRange` and `PhotoViewerInteractiveGestureTest.partialMediaPublicationKeepsGridVisibleUntilTheRangeIsFinal` also pass. The latter uses 40 real files and a provisional scan state with a genuinely scrollable published grid. Search, horizontal orientation, and custom-profile coverage remains open.
